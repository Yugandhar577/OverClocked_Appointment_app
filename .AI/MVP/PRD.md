## Architectural Step-Back — 5 Anchor Decisions

Every section below derives from these. They are non-negotiable.

**AD-1. Pre-materialized slot rows (not on-the-fly computation).**
`generated_slots` is a physical table populated by a slot-generation service. Booking, capacity, locking, and availability queries all operate on real rows. Cascade: publish/schedule-save triggers generation; every booking row FK-references a `generated_slot.id`; reschedule mutates two slot rows; availability endpoint is a single indexed SELECT.

**AD-2. Pessimistic row-locking via `SELECT … FOR UPDATE SKIP LOCKED` is the sole concurrency primitive.**
No optimistic versioning, no advisory locks, no application-level mutex. Every booking transaction begins with the lock query verbatim. Cascade: capacity is the single source of truth (`booked_count` column on slot row); two parallel writers cannot both proceed; "slot unavailable" and "slot full" produce the same 409 to the client but differ in audit_logs.

**AD-3. JWT-only stateless auth with role claims baked into token.**
No server-side sessions. Token carries `user_id`, `roles[]`, `exp`. Cascade: role checks are middleware-level (no DB hit), role mutation requires user re-login, refresh tokens are out of scope for MVP — access token TTL = 8h.

**AD-4. Service-layer state machine for `appointments.status`.**
All status transitions route through `appointment_service.transition(appt_id, target_status, actor)`. Invalid transitions raise `InvalidTransitionError` (HTTP 409). Cascade: cancel/reschedule/confirm endpoints are thin wrappers; audit_log row written per transition; reschedule = new row + old row marked `rescheduled` with FK back-reference.

**AD-5. Backend owns availability; frontend is dumb.**
Frontend never computes slot times, never derives capacity. It calls `GET /availability` keyed on (appointment_type_id, resource_id, date) and renders rows verbatim. Cascade: timezone math lives in backend; capacity decrement on cancel is server-side; frontend re-fetches availability after every booking action.

## 1. Product Overview

A multi-tenant appointment booking system with three roles (Customer, Organiser, Admin) replicating Odoo Appointments' core UX. Organisers configure appointment types with weekly working hours, resources, and intake questions; customers book slots through a date → slot → capacity → questions → confirm flow; admins manage users and roles. The system enforces zero-double-booking via pessimistic row locking, supports manual or auto-confirmation, mock-paid bookings, and reschedule/cancel within configured windows. Built in 24h by 4 devs as a FastAPI + React + PostgreSQL stack, fully testable across pytest, Supertest, and Playwright layers.

## 2. Architectural Decisions (detailed)

### AD-1 — Pre-materialized Slots
**Decision:** A nightly + on-demand job converts `working_hours` rows into discrete `generated_slots` rows for the next `future_days_limit` days (default 30). On `publish` or `working_hours` mutation, regeneration runs synchronously for slots in the future window; existing booked slots are preserved.
**Rationale:** Enables row-level locking, simple availability queries, deterministic capacity tracking. On-the-fly generation cannot use `FOR UPDATE SKIP LOCKED`.
**Implications:**
- New service: `slot_generation_service.regenerate(appointment_type_id)`
- Publish endpoint blocks until regeneration completes (typical < 500ms for 30 days × 16 slots)
- Slots beyond `future_days_limit` are generated by a daily cron at 00:05 UTC
- Reschedule = decrement old slot's `booked_count`, lock+increment new slot's `booked_count`

### AD-2 — Pessimistic Locking
**Decision:** Every booking write uses the exact SQL below inside a single `async with db.begin():` block.
```sql
SELECT * FROM generated_slots
  WHERE id = :slot_id AND is_blocked = FALSE AND booked_count < max_capacity
  FOR UPDATE SKIP LOCKED;
```
**Rationale:** Mandated by `appointment_db_design.docx`. SKIP LOCKED returns empty rowset to second contender immediately — no waiting, no deadlocks. No alternative considered.
**Implications:**
- Empty rowset → raise `SlotUnavailableError` → 409
- Same transaction performs `UPDATE generated_slots SET booked_count = booked_count + :n` and `INSERT INTO appointments`
- Cancel runs `SELECT … FOR UPDATE` (no SKIP) on the same row before decrementing
- Reschedule locks both old and new slots in a single transaction; lock order: old then new (sorted by id) to prevent deadlock

### AD-3 — JWT Stateless Auth
**Decision:** HS256 JWT, 8h TTL, payload = `{sub: user_id, roles: ["customer"|"organiser"|"admin"], exp}`. Sent via `Authorization: Bearer`. Stored in localStorage on client.
**Rationale:** Eliminates session table; horizontal scaling for free; role checks are pure middleware.
**Implications:**
- FastAPI `Depends(require_role("organiser"))` decorator pattern
- Forgot-password flow uses one-time short-lived JWT (15min) emailed as link query param
- Logout = client deletes token (no server revocation list for MVP)
- OTP verification flips `users.is_verified=TRUE`, then login issues JWT

### AD-4 — Status State Machine
**Decision:** All transitions in one service function. Allowed transitions:
```
pending     → confirmed   (organiser confirm OR auto-confirm)
pending     → cancelled   (any actor with permission)
confirmed   → completed   (cron after end_datetime)
confirmed   → cancelled   (within cancel_before_minutes window)
confirmed   → rescheduled (creates new pending/confirmed row)
```
**Rationale:** Centralized validation + audit trail; impossible to mutate status outside this path.
**Implications:**
- Direct `UPDATE appointments SET status=…` is forbidden in code review
- Every transition writes `audit_logs` row with `actor_id`, `before`, `after`, `reason`
- Completion runs as cron `SRC/Backend/jobs/complete_past_appointments.py` every 10 minutes

### AD-5 — Backend-Owned Availability
**Decision:** Single endpoint `GET /availability?appointment_type_id=&resource_id=&date=YYYY-MM-DD` returns `[{slot_id, start_datetime, end_datetime, remaining_capacity, max_capacity}]`. Client re-fetches on every relevant action.
**Rationale:** No client-side timezone bugs; capacity always fresh; simpler frontend.
**Implications:**
- All datetimes stored UTC; endpoint accepts client timezone offset query param `tz_offset_minutes`
- Frontend never holds a slot — booking POST sends `slot_id` directly
- Race window between availability fetch and booking POST is closed by AD-2's lock

## 5. Feature Specifications

### F-1 Auth & Onboarding
**Story:** As any user, I sign up with full name + email + password, verify via OTP, then log in to receive a JWT.
**AC:**
1. POST `/auth/signup` with `{full_name, email, password}` → creates `users` row with `is_verified=FALSE`, default role `customer`, generates 6-digit OTP, persists in `otp_verifications` (10-min TTL), emails OTP, returns 201.
2. POST `/auth/verify-otp` with `{email, otp}` → validates non-expired unused row, sets `is_verified=TRUE`, marks OTP `used=TRUE`, returns 200.
3. POST `/auth/login` rejects if `is_verified=FALSE` (403) or `is_active=FALSE` (403); else returns JWT (200).
4. POST `/auth/forgot-password` with `{email}` → emails password-reset link with 15-min JWT; always returns 200 to prevent email enumeration.
5. POST `/auth/reset-password` with `{token, new_password}` → validates JWT, updates `password_hash`, invalidates token (one-shot).

**Edge cases:** duplicate email → 409; OTP reused → 410; OTP expired → 410; password < 8 chars → 422; deactivated user attempts login → 403.
**Errors:** 409 EmailExists, 410 OtpExpired, 422 ValidationError, 403 AccountDisabled, 401 InvalidCredentials.

### F-2 Home / Appointment Type Discovery
**Story:** Any visitor sees a grid of published appointment types and can click "Book".
**AC:**
1. GET `/appointment-types?published=true` returns paginated list with `{id, title, duration_minutes, is_paid, price, organiser_name, preset_type}`.
2. Cards link to `/book/:appointment_type_id`.
3. Unpublished types are hidden from this list but accessible via `share_token` link `/book/share/:share_token`.

**Edge cases:** type unpublished after share-link generated → still accessible; deleted type → 404.
**Errors:** 404 AppointmentTypeNotFound.

### F-3 Booking Flow (Customer)
**Story:** As a customer I select service → resource → date → slot → capacity → answer questions → confirm.
**AC:**
1. GET `/appointment-types/:id` returns full config including resources, questions, booking_rules.
2. GET `/appointment-types/:id/resources` returns selectable resources when `assignment_method='by_visitor'`; if `automatically`, frontend hides selector and backend assigns least-loaded resource at booking time.
3. GET `/availability?appointment_type_id=&resource_id=&date=` returns slot list (AD-5).
4. If `manage_capacity=TRUE`, frontend renders party-size dropdown 1..min(remaining_capacity, max_capacity).
5. POST `/bookings` payload `{appointment_type_id, slot_id, resource_id?, people_count, answers: [{question_id, value}], customer_info: {full_name, email, phone}}` runs the locked transaction.
6. Success returns `{booking_id, status, confirmation_code, slot_start, slot_end, venue, organiser_name, payment_required, payment_url?}`.
7. If `is_paid=TRUE`, response includes `payment_url`; status stays `pending` until payment webhook (mock) confirms.
8. Confirmation page route `/booking/:id/confirmation` displays date, time, provider, venue, status, intake answers, cancel/reschedule buttons (visible only within window).

**Edge cases:** slot full (booked_count >= max_capacity) → 409; slot blocked → 409; concurrent same-slot writers → exactly one 201, one 409; missing required answer → 422; people_count > remaining_capacity → 409.
**Errors:** 409 SlotUnavailable, 409 CapacityExceeded, 422 IntakeAnswerMissing, 404 SlotNotFound, 402 PaymentRequired (P1).

### F-4 Profile & My Appointments
**Story:** As a customer I see my upcoming and past bookings; I can cancel or reschedule within window.
**AC:**
1. GET `/me/appointments?status=upcoming|past` returns paginated list ordered by start_datetime.
2. PATCH `/bookings/:id/cancel` allowed when current_time + cancel_before_minutes <= slot_start; decrements booked_count atomically.
3. PATCH `/bookings/:id/reschedule` body `{new_slot_id}`; runs reschedule transaction (AD-1, AD-4); old row → `rescheduled`, new row inserted with `rescheduled_from=:old_id`, status carries over (`pending` or `confirmed`).
4. GET `/me` returns user profile; PATCH `/me` updates `full_name`, `phone`.

**Edge cases:** cancel after window → 409 CancelWindowClosed; reschedule into full slot → 409; reschedule to same slot → 422.
**Errors:** 409 CancelWindowClosed, 409 SlotUnavailable, 422 SameSlotReschedule, 403 NotOwner.

### F-5 Appointment Type Configuration (Organiser)
**Story:** As an organiser I create an appointment type via preset, configure tabs (Availabilities | Questions | Communication | Options), publish, and share.
**AC:**
1. POST `/appointment-types` body `{title, preset_type, duration_minutes, resource_type: 'user'|'resource', timezone, future_days_limit, ...}` → creates row, generates `share_token` (UUID4), returns 201 with `is_published=FALSE`.
2. POST `/appointment-types/:id/resources` adds resource linkage; capacity defined per resource.
3. POST `/appointment-types/:id/working-hours` accepts array `[{day_of_week 0-6, start_time, end_time}]`; replaces previous set.
4. POST `/appointment-types/:id/questions` body `[{label, question_type, required, options[]}]`; replaces previous set.
5. POST `/appointment-types/:id/booking-rules` body `{requires_confirmation, manage_capacity, is_paid, price, advance_payment_required, cancel_before_minutes, reschedule_before_minutes, max_per_slot, future_days_limit, assignment_method}`.
6. PATCH `/appointment-types/:id/publish` → sets `is_published=TRUE`, triggers `slot_generation_service.regenerate(:id)` synchronously, returns 200 with first generated slot count.
7. PATCH `/appointment-types/:id/unpublish` → sets `is_published=FALSE`; existing bookings unaffected; future unbooked generated_slots get `is_blocked=TRUE`.
8. GET `/appointment-types/:id/share-link` returns `{url: BASE_URL/book/share/:share_token}`.

**Edge cases:** publish without working_hours → 422; publish without resources → 422; mutate working_hours after bookings exist → bookings preserved, only future unbooked slots regenerated.
**Errors:** 422 ConfigIncomplete, 403 NotOwner.

### F-6 Booking Management (Organiser)
**Story:** As an organiser I see all bookings on my types, filter by status, cancel/reschedule on customer's behalf.
**AC:**
1. GET `/organiser/bookings?appointment_type_id=&status=&date_from=&date_to=` paginated, default desc by created_at.
2. PATCH `/organiser/bookings/:id/confirm` (P1, when `requires_confirmation=TRUE`) → pending → confirmed; sends notification.
3. PATCH `/organiser/bookings/:id/cancel` allowed any time before slot start; same atomic decrement.
4. Calendar view backend: GET `/organiser/calendar?view=day|week|month&start=` returns bookings + blocked slots for grid render.

**Edge cases:** non-owner organiser → 403; confirm a non-pending booking → 409.
**Errors:** 403 NotOwner, 409 InvalidTransition.

### F-7 Admin Dashboard
**Story:** Admin manages users and roles.
**AC:**
1. GET `/admin/users?role=&is_active=&search=` paginated.
2. PATCH `/admin/users/:id/activate` → `is_active=TRUE`.
3. PATCH `/admin/users/:id/deactivate` → `is_active=FALSE`; future logins return 403.
4. PATCH `/admin/users/:id/roles` body `{roles: ["organiser"]}` → replaces user_roles entries; user must re-login.
5. GET `/admin/stats` returns `{total_users, total_organisers, total_customers, total_appointments, appointments_by_status: {…}}`.

**Edge cases:** deactivate own account → 422; demote last admin → 422.
**Errors:** 422 SelfDeactivationForbidden, 422 LastAdminProtected.

### F-8 Slot Generation Service
**Story:** System generates physical slot rows from weekly working_hours.
**AC:**
1. Triggered on: publish, working_hours update, resource attach/detach, daily cron 00:05 UTC.
2. For each day in `[today, today + future_days_limit]`, for each `working_hours` row matching `day_of_week`, for each resource, slice into `duration_minutes` chunks → upsert `generated_slots` rows with `is_blocked=FALSE`, `booked_count=0`, `max_capacity=resource.capacity`.
3. Existing rows with `booked_count > 0` are never deleted; if working_hours no longer covers them, they remain (preserve historical bookings).
4. Idempotent: re-run produces zero diff if config unchanged.

**Errors:** none surface to client; failures log to `audit_logs` with `event='slot_generation_failed'`.

### F-9 Reports (P1)
**AC:**
1. GET `/reports/summary?from=&to=&appointment_type_id=` returns `{total_bookings, peak_hours: [{hour, count}], provider_utilization: [{resource_id, name, booked_minutes, available_minutes, utilization_pct}]}`.
2. Frontend renders bar chart for peak hours, table for utilization.

### F-10 Notifications (P1)
**AC:**
1. On booking create with auto-confirm OR organiser confirm → send "Booking Confirmed" email.
2. On cancel → send "Booking Cancelled" email to customer.
3. SMTP via mailhog in dev; env var `SMTP_HOST` switches to real provider.
4. Failures retried 3× then logged to `notifications.status='failed'`.

## 7. Database Schema Summary

All 18 tables from `Documentation/appointment_db_design.docx` are implemented as-specified. **MVP deviations:** none — schema is fully implemented; only `flexible_slots` table goes unused (P2 feature) but the table exists per docx.

**Tables (by domain):**
- **Auth/RBAC:** `users`, `roles`, `user_roles`, `otp_verifications`
- **Config:** `appointment_types`, `resources`, `appointment_type_resources`, `booking_rules`, `appointment_questions`
- **Scheduling:** `working_hours`, `flexible_slots` (unused MVP), `generated_slots`
- **Booking:** `appointments`, `appointment_answers`, `slot_capacity_log`
- **Payments/Comms:** `payments`, `notifications`, `audit_logs`

**Critical indexes:**
```sql
-- AD-1 hot path (mandatory)
CREATE INDEX idx_generated_slots_lookup
  ON generated_slots (appointment_type_id, start_datetime, resource_id)
  WHERE is_blocked = FALSE;

-- Customer "my appointments" listing
CREATE INDEX idx_appointments_customer_status
  ON appointments (customer_id, status, slot_start_datetime DESC);

-- Organiser bookings filter
CREATE INDEX idx_appointments_type_status
  ON appointments (appointment_type_id, status, created_at DESC);

-- Auth lookups
CREATE UNIQUE INDEX idx_users_email_lower ON users (LOWER(email));
CREATE INDEX idx_otp_email_unused ON otp_verifications (email, used) WHERE used = FALSE;

-- Share link lookup
CREATE UNIQUE INDEX idx_appointment_types_share_token ON appointment_types (share_token);
```

**Concurrency lock pattern (verbatim, mandatory in every booking write path):**
```sql
SELECT * FROM generated_slots
  WHERE id = :slot_id AND is_blocked = FALSE AND booked_count < max_capacity
  FOR UPDATE SKIP LOCKED;
```

**Audit invariant:** every status transition writes one `audit_logs` row; every `booked_count` mutation writes one `slot_capacity_log` row with `delta` (+n on book, -n on cancel/reschedule-out).

## 8. Core Service Logic (Pseudocode)

### 8.1 Slot Generation — `slot_generation_service.regenerate(appointment_type_id)`
```
LOAD appointment_type, booking_rules
LOAD all working_hours WHERE appointment_type_id = :id
LOAD all linked resources (id, capacity)
horizon_end = today + booking_rules.future_days_limit days

FOR each date d in [today .. horizon_end]:
    dow = d.weekday()
    matching_wh = working_hours WHERE day_of_week = dow
    FOR each wh in matching_wh:
        FOR each resource in resources:
            slot_start = combine(d, wh.start_time, appointment_type.timezone)
            WHILE slot_start + duration_minutes <= combine(d, wh.end_time):
                slot_end = slot_start + duration_minutes
                UPSERT INTO generated_slots
                  (appointment_type_id, resource_id, start_datetime, end_datetime,
                   max_capacity, booked_count, is_blocked)
                  VALUES (:id, :resource.id, :slot_start_utc, :slot_end_utc,
                          :resource.capacity, COALESCE(existing.booked_count, 0), FALSE)
                  ON CONFLICT (appointment_type_id, resource_id, start_datetime)
                  DO NOTHING  -- preserves booked_count on existing rows
                slot_start = slot_end
RETURN count_of_inserted_rows
```

### 8.2 Booking Transaction — `booking_service.create(payload, actor)`
```
VALIDATE payload schema
VALIDATE answers cover all required questions for appointment_type
VALIDATE people_count >= 1

ASYNC WITH db.begin():            # opens single transaction
    -- AD-2 lock
    locked = EXECUTE """
        SELECT * FROM generated_slots
          WHERE id = :slot_id
            AND is_blocked = FALSE
            AND booked_count < max_capacity
          FOR UPDATE SKIP LOCKED
    """ WITH slot_id = payload.slot_id

    IF locked is empty:
        RAISE SlotUnavailableError      # → 409

    IF locked.booked_count + payload.people_count > locked.max_capacity:
        RAISE CapacityExceededError     # → 409

    IF appointment_type.assignment_method == 'automatically' AND payload.resource_id is NULL:
        resource_id = pick_least_loaded(appointment_type_id, locked.start_datetime)
    ELSE:
        resource_id = payload.resource_id OR locked.resource_id

    appt = INSERT INTO appointments (
        customer_id, appointment_type_id, slot_id, resource_id,
        slot_start_datetime, slot_end_datetime, people_count,
        status = (booking_rules.requires_confirmation ? 'pending' : 'confirmed'),
        confirmation_code = generate_code(),
        is_paid = booking_rules.is_paid,
        payment_status = (is_paid ? 'pending' : 'not_required')
    )

    INSERT INTO appointment_answers (appointment_id, question_id, value) FOR each answer
    UPDATE generated_slots SET booked_count = booked_count + :people_count WHERE id = :slot_id
    INSERT INTO slot_capacity_log (slot_id, appointment_id, delta = +people_count, actor_id)
    INSERT INTO audit_logs (event='booking.created', actor_id, target_id=appt.id, before=NULL, after='pending|confirmed')

    IF booking_rules.is_paid:
        payment = create_payment_intent(appt)   # P1: mock returns redirect_url
        attach payment_url to response

    enqueue_notification('booking_created', appt)   # P1
    COMMIT

RETURN appt response DTO
```

### 8.3 Reschedule — `booking_service.reschedule(booking_id, new_slot_id, actor)`
```
VALIDATE actor has permission (owner OR organiser-of-type OR admin)
LOAD original appt
VALIDATE original.status IN ('pending', 'confirmed')
VALIDATE current_time + reschedule_before_minutes <= original.slot_start_datetime
VALIDATE new_slot_id != original.slot_id

old_slot_id = original.slot_id
people_count = original.people_count

# Lock both slots in id-sorted order to prevent deadlock
ids_sorted = sorted([old_slot_id, new_slot_id])

ASYNC WITH db.begin():
    # Lock old slot (no SKIP — we own this row's capacity)
    EXECUTE "SELECT * FROM generated_slots WHERE id = :id FOR UPDATE" FOR each id in ids_sorted

    # Re-fetch new slot specifically with capacity guard
    new_slot = EXECUTE """
        SELECT * FROM generated_slots
          WHERE id = :new_slot_id
            AND is_blocked = FALSE
            AND booked_count + :people_count <= max_capacity
          FOR UPDATE SKIP LOCKED
    """
    IF new_slot is empty:
        RAISE SlotUnavailableError      # → 409

    # Decrement old, increment new
    UPDATE generated_slots SET booked_count = booked_count - :people_count WHERE id = :old_slot_id
    UPDATE generated_slots SET booked_count = booked_count + :people_count WHERE id = :new_slot_id

    INSERT INTO slot_capacity_log (slot_id=old, appointment_id=original.id, delta=-people_count, ...)

    # Mark old appointment rescheduled
    appointment_service.transition(original.id, 'rescheduled', actor)

    # Insert new appointment row inheriting answers & customer
    new_appt = INSERT INTO appointments (
        ... copy from original, slot_id=new, slot_start/end from new_slot,
        rescheduled_from = original.id,
        status = original.status   # preserve pending/confirmed
    )
    COPY appointment_answers FROM original.id TO new_appt.id
    INSERT INTO slot_capacity_log (slot_id=new, appointment_id=new_appt.id, delta=+people_count, ...)
    INSERT INTO audit_logs (event='booking.rescheduled', ...)
    enqueue_notification('booking_rescheduled', new_appt)
    COMMIT

RETURN {old_id: original.id, new_id: new_appt.id, status: new_appt.status}
```

### 8.4 Cancellation — `booking_service.cancel(booking_id, actor, reason)`
```
LOAD appt
VALIDATE actor permission
VALIDATE appt.status IN ('pending', 'confirmed')
IF actor.role == 'customer':
    VALIDATE current_time + booking_rules.cancel_before_minutes <= appt.slot_start_datetime
    ELSE RAISE CancelWindowClosedError   # → 409

ASYNC WITH db.begin():
    EXECUTE "SELECT * FROM generated_slots WHERE id = :slot_id FOR UPDATE"
    UPDATE generated_slots SET booked_count = booked_count - :people_count WHERE id = :slot_id
    appointment_service.transition(appt.id, 'cancelled', actor, reason)
    INSERT INTO slot_capacity_log (slot_id, appointment_id, delta = -people_count, actor_id, reason='cancel')
    INSERT INTO audit_logs (event='booking.cancelled', ...)
    enqueue_notification('booking_cancelled', appt)
    COMMIT
```

### 8.5 Status Transition — `appointment_service.transition(appt_id, target, actor, reason?)`
```
ALLOWED = {
    'pending':   {'confirmed', 'cancelled'},
    'confirmed': {'completed', 'cancelled', 'rescheduled'},
    'completed': set(),
    'cancelled': set(),
    'rescheduled': set()
}

LOAD appt
IF target NOT IN ALLOWED[appt.status]:
    RAISE InvalidTransitionError           # → 409

UPDATE appointments SET status = :target, updated_at = NOW() WHERE id = :appt_id
INSERT INTO audit_logs (event='status.transition', actor_id, target_id=appt_id,
                        before=appt.status, after=target, reason=reason)
```

## 10. Sequence Diagrams (text notation)

### 10.1 Booking Happy Path
```
Customer ─► Frontend         : selects type → date → slot → fills form → click Confirm
Frontend  ─► Backend         : POST /bookings { slot_id, people_count, answers, customer_info }
Backend   ─► PostgreSQL      : BEGIN
Backend   ─► PostgreSQL      : SELECT … FOR UPDATE SKIP LOCKED  (slot row)
PostgreSQL─► Backend         : returns 1 row (capacity available)
Backend   ─► PostgreSQL      : INSERT appointments
Backend   ─► PostgreSQL      : INSERT appointment_answers (n rows)
Backend   ─► PostgreSQL      : UPDATE generated_slots SET booked_count += :n
Backend   ─► PostgreSQL      : INSERT slot_capacity_log, audit_logs
Backend   ─► PostgreSQL      : COMMIT
Backend   ─► NotificationQ   : enqueue('booking_created') [P1]
Backend   ─► Frontend        : 201 { booking_id, confirmation_code, … }
Frontend  ─► Customer        : redirect /booking/:id/confirmation
```

### 10.2 Concurrent Double-Booking Race
```
Customer-A ─► Backend-A : POST /bookings  (slot 42, last seat)
Customer-B ─► Backend-B : POST /bookings  (slot 42, last seat)   [same instant]

Backend-A  ─► DB : BEGIN; SELECT … FOR UPDATE SKIP LOCKED  → ROW LOCKED to A
Backend-B  ─► DB : BEGIN; SELECT … FOR UPDATE SKIP LOCKED  → 0 ROWS (skipped)
Backend-B  ─► Customer-B : 409 SlotUnavailable               [returns immediately]

Backend-A  ─► DB : INSERT appointment, UPDATE booked_count, COMMIT
Backend-A  ─► Customer-A : 201 confirmation
```

### 10.3 Organiser Manual Confirm (P1)
```
Customer  ─► Backend : POST /bookings (booking_rules.requires_confirmation=TRUE)
Backend   ─► DB      : (locked tx) INSERT appointments status='pending'
Backend   ─► Customer: 201 status='pending'
Backend   ─► EmailQ  : 'awaiting_confirmation' to customer + organiser

Organiser ─► Frontend: opens /organiser/bookings, filter status=pending
Frontend  ─► Backend : GET /organiser/bookings?status=pending
Organiser ─► Frontend: clicks Confirm
Frontend  ─► Backend : PATCH /bookings/:id/confirm
Backend   ─► DB      : appointment_service.transition(:id, 'confirmed', organiser)
                       INSERT audit_logs
Backend   ─► EmailQ  : 'booking_confirmed' to customer
Backend   ─► Frontend: 200 status='confirmed'
```

### 10.4 Reschedule Flow
```
Customer  ─► Frontend : My Appointments → Reschedule on booking 100
Frontend  ─► Backend  : GET /availability?... (new date)
Customer  ─► Frontend : picks slot 250
Frontend  ─► Backend  : PATCH /bookings/100/reschedule { new_slot_id: 250 }

Backend   ─► DB : BEGIN
Backend   ─► DB : SELECT … FOR UPDATE  (slot 100.slot_id, sorted)
Backend   ─► DB : SELECT … FOR UPDATE SKIP LOCKED  (slot 250 with capacity check)
DB        ─► Backend : both rows locked
Backend   ─► DB : UPDATE old_slot booked_count -= n
Backend   ─► DB : UPDATE new_slot booked_count += n
Backend   ─► DB : transition(100, 'rescheduled')
Backend   ─► DB : INSERT appointments (id=101, rescheduled_from=100, status=carry-over)
Backend   ─► DB : COPY appointment_answers 100→101
Backend   ─► DB : INSERT slot_capacity_log×2, audit_logs
Backend   ─► DB : COMMIT
Backend   ─► Frontend: 200 { old_id:100, new_id:101 }
Frontend  ─► Customer: redirect /booking/101/confirmation
```
